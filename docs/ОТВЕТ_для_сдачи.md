Вариант: свой проект под реальную рабочую задачу.

**Что за проект.** «Ширма» — обезличивает файлы перед тем, как показать их
постороннему, и возвращает настоящие значения обратно, когда ответ получен.

**Откуда задача.** Я чиню чужие программы на заказ. Чтобы найти причину,
нужны логи и конфиги заказчика, а в них живут токены, пароли, телефоны и
фамилии. Отсюда тупик: заказчик боится давать доступ — работа не начинается;
даёт как есть — его секреты расходятся по чужим машинам. Это первый вопрос,
который мне задают на бирже, поэтому проект решает не выдуманную проблему.

**Почему нельзя просто замазать звёздочками.** Вместе с секретами пропадают
связи: если один и тот же ключ в десяти местах стал `***`, уже не понять,
один это ключ или десять разных и какой из них истёк. Поэтому метки
устойчивые: одна и та же компания везде становится `NAME_1`, один и тот же
ключ — `KEY_1`, в том числе в разных файлах. Смысл сохраняется, данные нет.

**Что внутри.** Веб-интерфейс на `127.0.0.1` (перетащил файлы — получил
обезличенные копии, словарь замен и отчёт), командная строка для папок,
15 тестов, скилл для Claude Code, README со скриншотами настоящего
интерфейса. Ни одной внешней зависимости — только стандартная библиотека
Python: через инструмент проходят чужие секреты, и чем меньше постороннего
кода в цепочке, тем меньше поводов ему не верить. По той же причине сервер
слушает только петлевой адрес, а страница не делает ни одного внешнего
запроса.

**Что оказалось самым полезным в работе.** Я прогнал MVP не на выдуманном
примере, а на настоящем логе — и нашёл четыре дефекта, невидимых при чтении
кода:

1. шаблон пути ждал один слэш, а в логах Windows их два — имя пользователя
   уходило заказчику открытым текстом;
2. «Петрова» в списке своих слов не ловила «Петровой» — фамилия оставалась
   в файле;
3. `words.txt`, сохранённый Блокнотом, начинается с невидимой метки, из-за
   неё первое слово списка не совпадало ни с чем — название компании молча
   утекало;
4. проверка перед отправкой считала секретами собственные метки, поэтому
   обезличенный файл всегда выглядел «грязным», а к таким предупреждениям
   быстро перестают прислушиваться.

Каждый закрыт тестом. Вывод, который забираю из урока: код, который
выглядит правильным, и код, который работает правильно, — разные вещи, и
различить их можно только измерением на настоящих данных.

**Про инструменты.** Публиковал через GitHub CLI, как в задании. Вход по
коду в браузере сначала не проходил — обрывалось соединение с эндпоинтом
устройства; разобрался, что дело в моём VPN, а не в CLI.
